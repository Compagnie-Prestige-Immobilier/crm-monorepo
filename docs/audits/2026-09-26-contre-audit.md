## 3. Nouveaux défauts bloquants (hauts)

### R01. Haute, CONFIRMÉ (CI) : les quatre parts Playwright échouent avant le premier test

- **Où** : `.github/workflows/ci.yml` job `parcours` (env sans `PUBLIC_WEB_URL` ni `SEED_FIXTURE_PASSWORD`) ; `cmd/server/main.go:384` (`publicWebURLRenseignee` appelée avant `-seed`) ; `cmd/server/seed.go:335-339`.
- **Cause** : le correctif de B119 exige `PUBLIC_WEB_URL` hors développement, y compris pour `./cpi-go -seed` ; le correctif de B57 exige `SEED_FIXTURE_PASSWORD` pour semer `crm_demo`. Le job n'a reçu ni l'un ni l'autre.
- **Preuve** : run 630, étape `Run ./cpi-go -seed` en échec sur les quatre parts, `pnpm test` sauté.
- **Impact** : aucun parcours e2e n'a tourné sur la remédiation ; B02, B11, B12 ne sont vérifiés que par lecture.
- **Correctif** : dans `env` du job `parcours`, `PUBLIC_WEB_URL: http://localhost:4000` et `SEED_FIXTURE_PASSWORD: fixtures-e2e-2026` (valeur déjà utilisée par `e2e/playwright.config.ts`).

### R02. Haute, CONFIRMÉ (reproduit) : l'import prospects CHUES importe la ligne d'exemple du modèle

- **Où** : `internal/imports/imports_adaptateurs.go:30-32` (disposition PROSPECTS : `premiereDonnee: 2` sans `exemples`) ; `internal/imports/imports.go:950-956` (`ligneExempleImport` rend `false` si `exemples == nil`) ; `internal/exports/exports.go:714` promet « La ligne 2 est un exemple grisé : elle n'est JAMAIS lue à l'import ».
- **Cause** : défaut antérieur (introduit par `cf53c720`), manqué par l'audit du 25 septembre. Le correctif de B38, qui refuse désormais un référentiel inconnu, l'a rendu visible.
- **Reproduction** : base neuve, `TestImportProspectsRelitLeModele` seul : échec sur « CBAO » ligne 2. Avec CBAO et CHUES présents (cas de la production) : la fiche « Ndiaye Aminata +221771234567 » est **créée** ; rapport `total=4` au lieu de 3. Dans la suite complète, le test ne passe que si `TestSeedEstIdempotent` (fichier `seed_…`, exécuté après `imports_…`) a déjà semé le référentiel : c'est pourquoi il est rouge en CI (base neuve) et parfois vert en local.

### R03. Haute, CONFIRMÉ (gitleaks) : clé API du classificateur JEV en clair dans l'historique git

- **Où** : `prompt.md:54` et `:89` à partir du commit `6fe6c7b3` (22 septembre), présente dans au moins sept commits (`git log --all -S JEV_API_KEY`). La suppression de `prompt.md` dans `4666da40` ne la retire pas de l'historique.
- **Impact** : toute personne ayant accès au dépôt, ou à un clone, peut utiliser la clé. Le job `gitleaks` restera rouge tant que l'historique la contient.
- **Correctif** : **révoquer et régénérer la clé chez JEV aujourd'hui**, la poser uniquement dans l'environnement Dokploy. Ensuite, décision du propriétaire : purge d'historique (`git filter-repo`, en même temps que les données personnelles de B16) ou exception gitleaks limitée à ces commits une fois la clé révoquée.
- **Second signalement** : `auth_integration_test.go:42` (`"fixtures-de-test-2026"`) est un faux positif ; le plus simple est de générer la valeur (`uuid.NewString()`) plutôt que d'ajouter une exception.

### R04. Haute, POTENTIEL (données) : la migration d'index unique peut bloquer le démarrage

- **Où** : `sql/migrations/20260925230100_lot_fiche_unique.sql:5-11` ; migrations appliquées au démarrage (`cmd/server/main.go:337`) avec `lock_timeout=5s` (`internal/shared/database/migrations.go:31`).
- **Cause** : aucun dédoublonnage avant `CREATE UNIQUE INDEX CONCURRENTLY`, alors que B30 décrivait des doublons possibles. Un seul doublon `(lotId, prospectId)` ou `(lotId, representantId)` fait échouer la migration à chaque démarrage : boucle de redémarrage. Par ailleurs l'attente d'un `CONCURRENTLY` derrière une transaction longue (export, tirage : jusqu'à 120 s) compte comme une attente de verrou et dépasse les 5 s.
- **Correctif** : avant déploiement, lancer sur la production `SELECT "lotId","prospectId",count(*) FROM lot_export_items WHERE "prospectId" IS NOT NULL GROUP BY 1,2 HAVING count(*)>1` (et l'équivalent représentants) ; si des lignes sortent, ajouter une migration de dédoublonnage avant celle-ci. Déployer hors pointe, ou créer les index à la main puis laisser goose enregistrer la version.

### R05. Haute, HAUTE CONFIANCE : la barrière de l'assistant (B18) et la procédure B53 se contredisent

- **Où** : `sql/migrations/20260925220000_assistant_lecture.sql:35` (`REVOKE EXECUTE ON FUNCTION pg_catalog.set_config(...) FROM PUBLIC`), aucun `GRANT assistant_lecture TO` ; `internal/assistant/sql_libre.go:80` (`SET LOCAL ROLE`) ; `infra/dokploy/README.md:320-324` (`ALTER ROLE crm NOSUPERUSER NOCREATEDB`).
- **Cause** : tout fonctionne aujourd'hui parce que `crm` est superutilisateur. Le jour où la procédure B53 est appliquée : `SET ROLE` est refusé (assistant en 422) ; `pg_dump`, qui appelle `set_config` dès la connexion, échoue (sauvegardes Dokploy, export admin, et donc `redeploy` bloqué au bout de 26 h par le garde-fou de B13) ; `NOCREATEDB` interdit les bases de démonstration. En outre `crm` est le superutilisateur d'amorçage de l'image `postgres:18.4` et ne peut pas être rétrogradé.
- **Correctif** : nouvelle migration `GRANT assistant_lecture TO CURRENT_USER; GRANT EXECUTE ON FUNCTION pg_catalog.set_config(text,text,boolean) TO CURRENT_USER;` ; dans le README, créer un rôle applicatif neuf `NOSUPERUSER CREATEDB` propriétaire des objets au lieu de rétrograder `crm`.
- **Vérification** : sur une base locale avec ce rôle, `pg_dump`, une question à l'assistant et la création d'une base de démonstration doivent réussir.
